Design proposal · emon_Suite live UI · revision 3 · October 2026

Shann Street Monitor Redesign

A phased plan to replace the Node-RED Dashboard 1 pages with a self-describing MQTT feed and one small web UI engine, emon-ui, whose pages are provisioned per site from emon_Suite/provisioning/<site>/, alongside the emon_config, Grafana dashboards and mosquitto config already kept there. It replaces the Instant Data tab at shannstainable and the six dashboard pages at enchantee with the same code.

What changed in revision 3. The race app and the event recorder are now in view as future consumers. They stay separate projects, but the design takes three things from them. The live UI follows the race app's proven transport, a small server that computes and pages that poll, rather than browsers subscribing to MQTT. Derived maths that today exists three times, in Node-RED, the race app and the recorder, moves into one shared library. And the envelope is shaped so both apps can migrate to it later on their own schedule. See the wider family.
Revision 2. Every site is now a first-class target, not only shannstainable. Page layouts move out of Node-RED git branches into the provisioning folder. A site can declare several pages, which covers enchantee's HUD, Dials, Navigation, Weather, Motor and Battery views. Derived values gain a declarative home in provisioning so they no longer need a site branch either. Sections marked revised or new below carry the changes.

What the current system does, and where it strains

The pipeline today is: radio nodes → emonSerialToMQTT → raw index topics such as power/0/2 → Node-RED flow context does all the arithmetic (daily totals, shower detection, tank days remaining, cost) → Dashboard 1 widgets. A second consumer, emonMQTTToInflux, re-parses the raw EmonLog lines and applies the names from emon_config.yml as Influx tags. The five issues you raised trace back to three structural causes.

Dashboard 1 is an Angular 1 grid from 2016It is officially deprecated and lays out groups by fixed widget widths (2×1, 8×1). It can't reflow into one phone column, has no CSS hooks per value, and so can't express "this number is old" without a template hack per widget. Issues 1, 2 and 3 are all this.
Names live in two places, by handemon_config.yml already says pulse channel 2 is "Consumed" and battery shunt 0 is "Bank 2". Influx uses that. Node-RED never sees it: flows switch on the last character of the topic and carry their own channelNames arrays (four commented-out versions of them). Issue 5.
Two parsers, one truthemon_mqtt.py and emon_influx.py are near-identical 400 and 750 line files, each decoding every payload type. Every new sensor or renamed channel is edited twice, and the MQTT copy drops the names on the floor. This is why issue 5 exists at all.
Site config is split across two reposEverything else per site lives in provisioning/<site>/: emon_config, docker-compose, Grafana dashboards, mosquitto, nginx. Node-RED alone keeps a git branch per site (nodeRed, Enchantee, harvey-farm), so a fix to shared flow logic is cherry-picked by hand and the branches drift. The UI is the bulk of what differs between those branches.
Daily totals live in Node-RED RAMEvery "today" figure is flow.get() arithmetic reset by cron at midnight. The daily email even warns "system was restarted, totals will not be accurate". Influx already holds the data to compute these robustly.

Three directions, one recommendation

Minor · stay inside Node-RED

Migrate to Dashboard 2.0

FlowFuse's @flowfuse/node-red-dashboard is the Vue/Vuetify successor. Responsive-ish grid, theming, ui-template with real Vue components, per-message CSS classes.

  • Keeps all flow logic and the email/backups untouched.
  • Staleness needs a Vue template per tile, or a global ticker in one template that dims by data-topic.
  • Still a widget grid: phone layout improves but stays a compromise. Every widget is rebuilt anyway, since D1 and D2 nodes are not interchangeable.
  • Names still hard-coded unless the publisher changes too.
Recommended · UI outside Node-RED

Small live service, pages that poll

A Python service, emon_live, subscribes to MQTT, keeps the latest value of every feed, runs the derived calculations and serves one JSON state document. One HTML/JS engine renders it, with no build step. Each site's pages are JSON files in its provisioning folder that reference feeds by name. This is the race app's architecture, generalised.

  • CSS grid with media queries: 4 columns on a desk, 2 on a phone, same page. Held to the race app's iOS 12 floor, so it runs on the boat's iPad mini 3.
  • The server sends every value with its age, so fading and blanking is one client rule that never depends on a phone's clock.
  • Colour, units, and layout are data, not widget configuration.
  • Node-RED keeps doing what it is good at: the daily email and log backups. Derived figures move to emon_live, and are published back to MQTT for the race app and recorder.
Deep · change what is published

Self-describing MQTT + one decoder

Refactor pyemonlib so a single decoder turns a serial line into a list of readings (value, unit, kind, node, sub, index, group, name). Sinks are tiny: MQTT publishes a JSON envelope on a new emon/ namespace, Influx tags from the same record.

  • Kills the duplication between the two 400 and 750 line files.
  • Node-RED, the web UI, and Influx all get names automatically, and renames in a timestamped settings file propagate everywhere at once.
  • Legacy topics keep publishing until every consumer has moved.
  • This is the change that makes the recommended UI cheap to build. Do it first.
Not recommended as the main path: rebuilding the instant view in Grafana. Stat panels with last() cover most tiles and colour thresholds are free, but Grafana on a phone is poor, "stale" can only be expressed as no-data over a time window, and the derived values still need to come from somewhere. Worth a quick trial only if you want zero new code.

Proposed architecture revised

Two rules organise everything. Code lives once in emon_Suite, and everything that differs between sites lives in provisioning/<site>/. That is already true for the publishers, Influx, Grafana and mosquitto, and this extends it to the live UI and the derived values. Calculations live once, in a pure library with no I/O, so the live service, the race app and the recorder compute TWA, distance or energy identically, and replay tests cover them all.

The envelope

Topic path stays structural (stable across renames, unique by construction) and mirrors the existing raw topics one level down; names ride in the payload. Published with retain=True so a phone opening the page cold shows every last value, correctly aged, before a single new message arrives.

emon/power/0/2            ← kind / node-subnode / index   (legacy power/0/2 still published)
{
  "v": 2867,                 value, already scaled
  "u": "W",                  unit
  "t": 1757580061,           unix seconds, host clock at receipt
  "kind": "power",
  "node": "pulse", "sub": 0, "idx": 2,
  "group": "Power board",    nodeSettings[sub]["name"]
  "name": "Consumed",        nodeSettings[sub]["p2"]
  "rssi": -61                 when present
}

emon/config                ← retained, JSON of the active settings file + its filename
emon/derived/power/today/consumed   ← emon_live publishes (Node-RED, until emon_live exists)
{ "v": 18452, "u": "Wh", "t": …, "name": "Consumed today", "kind": "energy" }

Two clocks, stated once. t is the bridge host's clock when the line arrived, as gps/position already documents. Consumers on the same host may use it, and must for retained messages, whose arrival time is only the moment of subscribing. Browsers never see t: emon_live sends age, as the race app does, so a phone whose clock is a minute out still dims correctly. Event payloads such as race/event keep their own fields but gain t and kind: "event", so the recorder can store them like any other feed.

Two side benefits fall out of this. Influx tags sensor, sensorGroup, sensorName map one-to-one to node/sub/idx, group, name, so nothing in Grafana changes. And the retained emon/config lets Node-RED replace its hard-coded channelNames arrays with one lookup, even before the UI is touched. Two small existing inconsistencies get fixed on the way: bms/voltage{n} and sevCon/rpm{n} are missing the slash before the subnode.

A site's UI is a folder of plain files next to its emon_config. Nothing UI-specific is built into an image, and the engine never contains a site name.

Pages are addressed as /#hud, /#dials and so on, so the Waveshare kiosk launcher keeps a fixed URL per screen. A link entry puts another app in the menu without owning it, which is how the race app's HUD and race screen appear. An entry with "for": "phone" appears first in the menu on narrow screens. Shannstainable has a single page and shows no menu at all.

Feeds referenced by name

Pages refer to feeds as group / name, exactly as written in emon_config, for example Power board / Consumed. Nodes whose fields carry no names in config, such as bms, gps and imu, use the field itself: Main Battery / batterySoC. Where one channel publishes two kinds, the kind is appended in brackets, as in Power board / Consumed (pulse) for the counter beside the instantaneous watts. The engine resolves names against the retained emon/config topic at load. Two things follow. When a sensor moves to a different channel in a new timestamped settings file, the page follows it without an edit. When a sensor is renamed, the page breaks loudly instead of showing the wrong number, because lint_pages.py runs against the same provisioning folder and is cheap to run in the build script or as a check in emon_settings_web before it saves a new settings file. A structural topic such as emon/power/0/2 is still accepted for feeds with no config entry, such as ecowitt.

How it is served, and why polling

Revision 2 had browsers subscribe to mosquitto over websockets. The race app's design brief considered that and chose polling instead, for reasons that hold for emon-ui. Polling works unchanged across AP mode, mDNS, raw IP and nginx prefixes. It needs no broker change and no vendored MQTT client, and a wifi dropout heals itself on the next request. It also lets derived values be computed once on the server instead of in every open browser. So emon-ui polls.

  • emon_live is one Flask container per site, like the race app. The engine's static files and the site's emon-ui folder are bind-mounted, so edits are live, matching "the checkout is the deployment". It serves the pages and /api/state from one port.
  • enchantee: host nginx maps / to emon_live in place of Node-RED's /ui/, which moves to /nodered/ui/ during the overlap. /race/ and /events/ are untouched.
  • shannstainable and the other sites publish emon_live's port, or put it behind the existing reverse proxy for https.
  • Poll rate is 1 s by default and 500 ms for any page that asks for it, matching the HUD. The state document is small and gzipped, as the race app's is.
  • Browser floor is the race app's: iOS 12, no CDNs, relative URLs, no clamp() or flexbox gap, and every SVG given a width and height. The day and night theme is server state, so every screen on the boat switches together. That is a lesson recorded in the race app's design brief.

Derived values in provisioning

Most of what the Node-RED function nodes compute is one of a handful of shapes. Expressing those shapes as config lets every site have them without a branch. The operators are emon_feed functions, so a derived.yml line and a call in the race app or recorder produce the same number.

# provisioning/shannstainable/emon-ui/derived.yml
- id: power/consumed/today
  op: daily_delta             counter → amount since local midnight
  feed: Power board / Consumed (pulse)
  scale: 2.5                  Wh per pulse, from emon_config p2_wPerPulse when omitted
- id: solar/today
  op: sum
  of: [Power board / Solar production (Schneider) (pulse), derived/inverter1/today, derived/inverter3/today]
- id: inverter1/today
  op: integrate               W → Wh, trapezoidal, gaps over 5 min not bridged
  feed: Inverter 1 / PV input
- id: import/cost/today
  op: expr
  expr: "derived/import/today / 1000 * 0.262"
  unit: "$"
- id: rain/since9am
  op: daily_delta
  feed: Outside / Rain
  reset: "09:00"

# provisioning/enchantee/emon-ui/derived.yml
- id: wind/twa
  op: twa                     norm180(twd - hdg), as the race app computes it today
  twd: True wind / windDirection
  hdg: IMU Sensor / heading
- id: wind/awa
  op: awa                     measured AWA if fresh, else norm180(awd - hdg)
  awa: Boat reference wind / windDirection
  awd: Apparent wind / windDirection
  hdg: IMU Sensor / heading
- id: boat/leeway
  op: leeway                  ported from enchantee_racing store.derive_leeway
- id: boat/heel
  op: heel                    from IMU acc y and z, ported from derive_heel
- id: battery/energy/today
  op: integrate
  feed: Main Battery / power

On start the service asks Influx for each counter's first value since the reset time, so a restart mid-afternoon resumes the right totals. That retires the "system was restarted" warning in the daily email. Every derived feed is also published back to MQTT, which is what lets the recorder chart TWA, leeway and heel without computing them itself. Shower detection, the dog-fed email and the rolling tank-use average stay in Node-RED for now, since they are bespoke state machines that only one site has.

Node-RED without branches

Once the dashboards are gone, the remaining flows are small. Move each site's flows.json to provisioning/<site>/node-red/ and set flowFile in the shared settings.js from an environment variable, with package.json and entrypoint.sh kept once on the main branch. The compose volume becomes the shared repo plus the site folder. The three branches can then be archived. The dashboard-only dependencies (ui-led, ui-level, ui-value-trail, ui-iframe, node-red-dashboard) drop out, which also shortens the start-up npm install on the Pi.

The wider family: race app and event recorder new

Neither project is refactored as part of this work. Each has its own design brief, its own CLAUDE.md and its own tests, and each will migrate when it is next worked on. What this work owes them is a contract they can migrate to, and shared code they can import rather than copy.

enchantee_racing, when it migrates

  • Topics become names. The TOPICS map turns from anemometer/windDirection/0 into Boat reference wind / windDirection. That one change makes the subtle 0, 1 and 2 mapping in its design brief readable, and a re-wired anemometer becomes an emon_config edit.
  • Derived maths is imported, not owned. derive_leeway, derive_heel and the TWA and AWA fallback move into emon_feed with their tests. The race app either imports them or reads emon/derived/wind/twa. The race engine itself, legs, marks and line crossing, stays in the app: it is race logic, not a feed.
  • Its rules are kept, not loosened. Position stays one atomic payload and blanks after 5 s. Staleness still counts from arrival. Bare-number legacy topics keep publishing until the app has moved, so the migration can happen between races, not during one.
  • Its store becomes the shared store. emon_live's state model is the race app's store.py pattern lifted into pyemonlib. Writing emon_live is the moment that pattern gets its second user, which is when it is worth extracting.

event_recorder, when it migrates

  • A recording keeps its own names. On start, the recorder stores the retained emon/config as a snapshot beside the rows. Every chart then labels itself from the snapshot, so a sensor renamed next month does not relabel last month's post.
  • Plots configure by name or kind, not topic. Today a plot names each topic and repeats its label, unit and colour by hand, and the speed plot is labelled km/h where the race app documents knots. With units in the envelope that class of error goes away. A plot can say kind: power and get every battery bank, labelled and in domain colours.
  • Derived feeds are recorded like any other. Because emon_live publishes TWA, leeway and heel, the recorder can chart them with a line of config and no new maths. Race events gain t and kind, so they can be drawn on the same time axis as the instruments.
  • Statistics share the arithmetic. Distance and energy come from emon_feed, so the post, the live summary and the race app agree to the metre.
  • Wildcards get simpler. Recording emon/# captures everything with names. The slashless bms/voltage1 topic that today needs a separate bms/+ line is fixed in the new namespace.

The contract both can rely on

  • The envelope is versioned with a field s: 1. Fields may be added, never renamed or removed, within a version.
  • Legacy topics publish until the last consumer has moved. Node-RED, the race app, the recorder's existing configs and Grafana's raw topic queries all keep working throughout.
  • emon_feed parses both forms. parse(topic, payload) returns a reading from an envelope or from a bare number, so either app can switch its parsing first and its subscriptions later.
  • emon_feed has no I/O, the same rule as the race app's engine/, so all three projects can replay-test against the recorded Frostbite tracks.

Data age, three states

Every tile shows the age of its newest feed. The server sends each value's age, and the page adds the time since its last poll, so ages keep counting if the wifi drops and never depend on the phone's clock. The rule is the same for raw sensors and derived values.

Thresholds are per feed in the layout JSON, because "old" differs: a 10 s pulse channel and a once-a-day odometer should not share a 60 s rule.

Layout is data

A tile is a few lines of JSON naming feeds. Adding a sensor is: name it in emon_config.yml, add one entry to the site's page file. No Node-RED nodes, no widget widths, no branch.

// provisioning/shannstainable/emon-ui/pages/house.json  (one tile of many)
{
  "title": "Hot water", "domain": "heat", "span": 1,
  "fresh": 60, "gone": 300,
  "hero":  [ {"feed": "Hot water system / Water (T3)", "label": "Tank", "decimals": 0},
             {"feed": "derived/hws/showersRemaining", "label": "Showers left"} ],
  "gauge": {"feed": "derived/hws/showersRemaining", "max": 27},
  "line":  "Today {derived/hws/showers} showers · {derived/hws/showerMinutes} min · {Rain tank and HWS / Hot water} L"
}

Decisions to confirm revised

  • Polling rather than websockets. Recommended, following the race app's reasoning. The cost is one small service per site, which is also where the derived values need to run anyway.
  • Feeds by name or by topic. Recommended: pages and derived.yml name feeds as group / name from emon_config, with a lint check guarding renames. The same lint can later check the recorder's event configs.
  • Who computes TWA on the boat. Recommended: emon_live publishes it and the race app imports the same function rather than reading the feed. The race app then keeps working if emon_live is down, which matters more on the water than one fewer calculation.
  • Where emon_feed lives. Recommended: inside pyemonlib, since every image already installs that wheel. The race app does not install it today, so its migration adds one wheel to its Dockerfile.
  • How far to take derived.yml. Shower detection and the dog-fed email could become operators later, or stay in Node-RED. I would leave them until a second site needs them.
  • Data-age thresholds. A site default in site.json, overridable per tile. Suggested 60 s and 5 min for the house, and 15 s and 2 min on the boat to match the HUD. Position keeps the race app's 5 s blanking.
